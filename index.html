Geste 4 — chargement du widget embarquable en cross-origin (D-28, BUILD-05)

Extrait d'intégration exact, tel qu'un salon le collerait sur son site — le defer est posé dès ce premier exemple, jamais ajouté après coup (Pitfall 17) : un intégrateur copie l'exemple qu'on lui donne, et corriger la documentation plus tard ne récupère pas les balises déjà collées. 

<script defer src="https://booking-api-psi-lilac.vercel.app/widget/v1/booking-widget.js"></script>
<booking-widget salon="salao-demo"></booking-widget>

Ce qu'il faut observer ci-dessous : les prestations actives du salon salao-demo s'affichent en pt-BR, rendues dans un shadow root Lit chargé depuis booking-api-psi-lilac.vercel.app — un domaine distinct de celui qui sert cette page (*.github.io), donc en cross-origin réel. Le tunnel permet de choisir une prestation, puis un employé (ou « peu importe »), puis un créneau dans le fuseau du salon ; le récapitulatif affiche le choix complet SANS jamais poster de réservation (écran terminal de la Phase 10). Toutes les requêtes émises par le widget visent l'origine de l'API, jamais une autre. L'URL du script est volontairement laissée en dur (pas dérivée d'apiOrigin/?api=) : ce bloc doit rester l'exemple copiable exact, jamais une variante paramétrée qu'un intégrateur ne pourrait pas coller telle quelle.

Ce que cette page ne prouve pas

  • Le détail du préflight OPTIONS lui-même : il est géré en interne par le navigateur et invisible à JavaScript — ni le geste 1, ni le geste 3 ne peuvent l'observer. Seul DevTools ou un curl -X OPTIONS manuel montre son détail exact.
  • Tout en-tête de réponse d'API non listé par Access-Control-Expose-Headers — cet en-tête n'est jamais émis par server/http/publicResponse.ts, donc cette page ne peut lire que le statut HTTP et le corps JSON des réponses de l'API, jamais un en-tête personnalisé au-delà de la petite liste CORS-safelisted.
  • La latence depuis le Brésil — mesurée séparément par une sonde tierce distribuée (type Globalping), pas par cette page (D-15).
